We're planning to do some larger/longer training runs in the relatively near future -- on the order of weeks to months, and using hundrerds of GPUs. At this scale (small for the LM field generally, but large for us), node/GPU failures become a real risk, and my assumption is that for runs near the higher end (> a month, on the order of 64 nodes, so 512 GPUs) I'd expect a failure once a week or perhaps even every few days. I want to make sure we're as resilient as possible: 1) appropriate checkpointing, both in terms of interval and also making sure that we're actually saving everything we need to save at each checkpoint to rapidly perform a bitwise-clean resume; and 2) make sure we're managing everything correctly on the SUNK (CoreWeave's slurm on kubernetes) end so that resumes can happenen automatically on failures. Let's brainstorm about what in the codebase works alreacy, what's kinda there but needs some work to make optimally robust, and what's missing entirely and needs to be built from the ground up.

## Async / distributed / atomicity / retention
- **Blocking.** `save_state` is a synchronous `torch.save`/`safe_save_file`; `save_checkpoint` ends with `accelerator.wait_for_everyone()` (`checkpoint.py:85`). No async/background save, no double-buffering.
- **Rank-0-only for the heavy artifacts.** Model/optimizer/scheduler go through `accelerate.utils.other.save()` which writes only on `PartialState().is_main_process` (`save_on_each_node=False`). RNG files are per-rank. `trainer_state.json`, `config.yaml`, `hf/`, and rotation are inside `if accelerator.is_main_process:` (`checkpoint.py:57`).
- **NOT torch.distributed.checkpoint / DCP.** No `torch.distributed.checkpoint` import anywhere in `src/`. No FSDP/DeepSpeed path is active (DeepSpeed is explicitly disabled unless `OPLM_ENABLE_DEEPSPEED`, `src/oplm/train.py:23-83`).
- **No atomic write.** `grep` for `os.replace`/`.tmp`/`rename(` in `src/` returns **nothing**. Files are written in place into `checkpoint-&lt;step&gt;/`; a kill mid-write leaves a partial directory.
  - Mitigating accident (**INFERRED**, not designed): `trainer_state.json` is written *after* `save_state`, and `load_checkpoint` hard-fails if it's missing (`checkpoint.py:114-116`), so a torn checkpoint usually raises `FileNotFoundError` rather than silently resuming from garbage. - **Rotation:** `_rotate_checkpoints` (`checkpoint.py:122-135`) sorts by numeric step suffix and `shutil.rmtree`s the oldest beyond `save_total_limit` (default 3). `save_total_limit &lt;= 0` disables rotation. Tested: `tests/training/test_checkpoint.py:158-176`, `tests/training/test_e2e_checkpoint.py:41-76`.
- **No `latest` symlink, no pointer/manifest file.** Nothing writes a `latest`/`LATEST`/`last_checkpoint` marker. Discovery is by directory-name scan only.

# 2. RESUME

## Mechanism
- **Single knob:** `train.resume_from: str | None` (`src/oplm/config.py:89`, `configs/train/base.yaml:60`). It is a **config field, not a CLI flag** — set as `oplm train ... train.resume_from=outputs/run/checkpoint-50000` (`docs/TRAIN.md:327-334`, `docs/CONFIG.md:269`). The CLI (`src/oplm/cli.py:81-99`) has only `--config/--preset/--name/overrides`.
- `Trainer.__init__` (`trainer.py:263-266`):
  ```python
  if cfg.train.resume_from is not None:
      _status("[dim]Resuming from checkpoint...[/dim]")
      self._resume_from_checkpoint(cfg.train.resume_from)
  ```
- **`oplm.train` does NOT auto-detect the latest checkpoint.** Documented explicitly: `docs/SLURM.md:291-293` — *"`oplm.train`'s `Trainer` only resumes when `train.resume_from` names a checkpoint directory explicitly … it does not scan `train.output_dir` for the newest checkpoint on its own."*
- **Auto-detect exists only in the sweep runner:** `src/oplm/sweep/run.py:15-40` (`latest_checkpoint`, numeric-suffix max) and `:63-66`:
  ```python
  if cfg.train.resume_from is None:
      checkpoint = latest_checkpoint(Path(cfg.train.output_dir))
      if checkpoint is not None:
          cfg.train.resume_from = str(checkpoint)
  ```
  Only `oplm.sweep.run` (the module launched by sweep array jobs, `phases.py:377`) gets this. Plain training jobs generated by `oplm slurm generate` launch `oplm.train` (`slurm/cli.py:77-79`) and therefore **restart at step 0 on requeue** unless someone edits the config.

## What gets restored
`trainer.py:542-568` + `checkpoint.py:88-119`:
- Via `accelerator.load_state`: model weights, **all** optimizer states (incl. Muon momentum buffers), all scheduler states, GradScaler (fp16 only), per-rank RNG (python/numpy/torch-CPU/torch-CUDA), accelerate's internal `step`.
- From `trainer_state.json`: `global_step`, `epoch`, `tokens_seen`, `samples_seen` (with a back-compat fallback `global_step * effective_batch`, `trainer.py:550-552`).
- `self._set_dataset_epoch(self.epoch)` (`trainer.py:553`) → `DataLoaderShard.set_epoch` → `IterableDatasetShard.set_epoch` → `ShardedProteinDataset.set_epoch` (verified chain: `accelerate/data_loader.py:613-630`, `:320-323`; `src/oplm/data/sequence/dataset.py:177-187`).
- `_epoch_at_last_opt_step` and `_step_local_tokens` reset (`trainer.py:555-559`).
- **RNG caveat:** accelerate swallows RNG-load failures — `except Exception: logger.info("Could not load random states")` (`accelerate/checkpointing.py:315-316`). If the world size grew, `random_states_&lt;rank&gt;.pkl` is missing for new ranks and the failure is silent.

## Is resume exact/bitwise?
**No, and the repo says so.** `tests/training/test_e2e_checkpoint.py:11-15` (module docstring):
&gt; *"OPLM's training stream is an `IterableDataset` that restarts at the top of the epoch when a resumed trainer rebuilds its iterator, so the exact sequence of post-resume batches (and therefore `tokens_seen`) does not match an uninterrupted run. We assert counter *restoration* and trajectory *continuity* rather than bit-exact equivalence against a non-resumed control."*

Concretely: `Trainer.train()` does `data_iter = iter(self.dataloader)` at `trainer.py:300` with **no skip-ahead**, so a run resumed at step 50 000 re-reads the epoch from row 0. **Data is re-seen; no sample-skipping mechanism exists.**

## Tests of resume correctness (EXISTS)
- `tests/training/test_e2e_checkpoint.py:115-174` — train to step 4, checkpoint, fresh `Trainer` with `resume_from`, assert restored `global_step`/`tokens_seen`/`samples_seen`/`epoch`; post-resume logs cover exactly steps 5–8; LR at step 5 matches `get_schedule_fn(..., total_steps=8)(5)`; loss-continuity band `0.2 &lt; first_post/last_pre &lt; 5.0`. **No loss-equality test vs. an uninterrupted control.**
- `tests/training/test_checkpoint.py:105-124` — `load_checkpoint` returns metadata; `:55-77`/`:127-155` HF export round-trip (incl. `torch.compile`); `:158-176` rotation.
- `tests/sweep/test_run.py:46-100` — requeue simulation: second run with `resume_from` unset resumes from `checkpoint-2`; asserts `checkpoint-1`'s mtime is unchanged (proof it didn't restart at 0).
- `tests/training/test_e2e_checkpoint.py:78-112` — `save_final` on/off.

# 3. DATA PIPELINE

- **Custom iterable parquet reader.** No webdataset, no HF `datasets` streaming, no map-style dataset, no `DistributedSampler`.
  - `src/oplm/data/sequence/dataset.py`: `ShardedProteinDataset(IterableDataset)` (line 97) over `.parquet/.parq/.pq` files or a directory of shards; `InterleavedDataset(IterableDataset)` (line 260) mixes several sources by fraction.
  - `src/oplm/data/sequence/loaders.py:42-99` `build_train_dataloader` → plain `torch.utils.data.DataLoader` (`:158-180`) with `num_workers`, `pin_memory`, `prefetch_factor` from `data.*`.
- **Sharding:** the dataset does its own rank/worker striping — `_resolve_distributed_context()` (`dataset.py:57-81`, uses `dist.get_rank()` or `RANK`/`WORLD_SIZE` env) and `_joint_stripe()` (`:84-94`, `joint_index = rank*num_workers + worker_id`, `stride = world_size*num_workers`); `__iter__` selects rows where `(base + offset) % stride == joint_index` (`:206-229`).
  - **Note (INFERRED, worth checking):** under multi-process, `accelerate.prepare_data_loader` additionally wraps any `IterableDataset` in `IterableDatasetShard` (`accelerate/data_loader.py:1213-1231`), which itself yields only every `process_index`-th batch. That is a *second* layer of rank sharding on top of the dataset's own striping. I found no code, comment, or test in this repo that acknowledges it. Under `num_processes = N` this would mean each rank consumes ~1/N of its already-1/N stripe.
- **Deterministic resume: NO.** There is no `state_dict`/`load_state_dict` on either dataset, no row/shard cursor, no "skip to sample K". Resume restarts the epoch (`trainer.py:300`, and the epoch-rollover path `:307-313`). Consequences are documented for eval cadence too: *"Epoch cadence is deferred precisely because a mid-epoch checkpoint restarts the dataloader at the epoch start"* (`docs/OVERVIEW.md:1244-1247`).
- **Shuffle seed handling (deterministic, epoch-keyed):** `dataset.py:37-49`
  ```python
  _PHI = 0x9E3779B97F4A7C15
  def _epoch_seed(base, epoch): return ((_PHI ^ base) + epoch * _PRIME) &amp; _MASK32
  def _shard_row_seed(epoch_seed, s): return (epoch_seed + 1009 + s) &amp; _MASK32
  ```
  Shard order (`:189-196`) and per-shard row order (`:198-204`) are `torch.randperm` under a manual-seeded `torch.Generator` — pure functions of `(seed, epoch)`, identical across ranks and runs. Base seed = `cfg.train.seed` (`loaders.py:72`, `:84`, `:96`). `InterleavedDataset` seeds source choice per `(epoch, rank, worker)`: `manual_seed((_epoch_seed(seed, epoch) + joint_index) &amp; _MASK32)` (`dataset.py:343-348`).
  - So: **shuffle order is reproducible; position within it is not persisted.** Resuming at the same `epoch` replays the same order from the start.
- **Masking RNG:** training uses `deterministic=False` → the collator uses the *global* torch RNG in each worker (`src/oplm/data/sequence/collate.py:240-253`, `generator = None`), so masks are not reproducible across a restart (worker RNG is re-seeded by DataLoader worker seeding, not by the checkpointed RNG state). Eval uses `deterministic=True` with a per-batch counter seed + `_ResettingDataLoader` (`loaders.py:140-155`).
- `set_epoch` propagation is the only per-epoch state (`trainer.py:479-487`).

# 6. OTHER FAULT-TOLERANCE-ADJACENT

**Exists:**
- **NCCL:** only `export NCCL_DEBUG=INFO` in the generated script (`render.py:140`). **No `TORCH_NCCL_*` settings, no `NCCL_TIMEOUT`, no `InitProcessGroupKwargs(timeout=...)`, no `TORCH_NCCL_ASYNC_ERROR_HANDLING`, no `TORCH_NCCL_HEARTBEAT_TIMEOUT_SEC`, no flight-recorder/dump settings.** The default 10-minute NCCL watchdog applies unmodified (**INFERRED**).
- **Rank-sync invariant** (the main hang-avoidance design): every field of `EvalContext` is rank-identical so all ranks agree on `is_due` and enter collectives together — `trainer.py:356-364` unconditionally rank-reduces per-step tokens; design rationale at `docs/OVERVIEW.md:1180-1191` (*"a per-rank `is_due` disagreement would hang at the NCCL timeout"*). Schedules are pure functions with no persisted counters, hence resume-safe (`docs/OVERVIEW.md:1195-1198`, `src/oplm/eval/schedule.py`).
- Related: the stability-diagnostics probe is deliberately main-process-safe/collective-free — comment at `src/oplm/training/mup.py:351` and `docs/LR_SWEEP.md:480` (a prior probe that ran on every rank *"hung multi-GPU runs with an NCCL timeout"*).
- **Eval is fully blocking/inline** — `Evaluator.run_due` runs synchronously in the training loop (`trainer.py:381`, `src/oplm/eval/evaluator.py:72-92`). No background/non-blocking eval, no separate eval job. The step timer is restarted after eval/checkpoint so their wall time is excluded from throughput (`trainer.py:405-407`).

- **Environment bootstrap** `_bootstrap_training_environment` (`src/oplm/train.py:68-83`): forces a writable `TRITON_CACHE_DIR` (`~/.cache/oplm/triton/autotune` → tmp fallback) and disables DeepSpeed env leakage unless `OPLM_ENABLE_DEEPSPEED`. Prevents a class of ephemeral-pod startup failures.

## Summary of the concrete gaps for a long multi-node run

1. Dataloader position is never checkpointed and cannot be — resume replays the epoch from row 0 (data re-seen, epoch-boundary accounting drifts).
2. `oplm.train` does not auto-resume; only `oplm.sweep.run` does. A requeued production `oplm slurm generate` job silently restarts at step 0.
3. No SIGTERM/SIGUSR1 handling → preemption/time-limit loses everything since the last `save_every` (10 000 steps by default in `configs/scaling.yaml`).
4. `max_restarts=0`, static rendezvous → any single-node failure kills the whole job; requeue restarts the container from scratch.
5. Non-atomic checkpoint writes + name-based "latest" selection → a torn checkpoint makes sweep auto-resume raise instead of falling back.
6. W&amp;B starts a new run on every resume (no run-id persistence).
7. No NCCL timeout/async-error-handling tuning; only `NCCL_DEBUG=INFO`.</result>
